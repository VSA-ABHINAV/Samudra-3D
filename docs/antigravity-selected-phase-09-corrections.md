## Required corrections

1. **Cancellation must stop the downloader process tree and close process-registration races.** The Windows helper ignores `taskkill`'s return code, then kills the shell and verifies only `proc.poll()`. If taskkill fails but killing the parent works, it can still report success while a Copernicus child remains alive. There is also a launch race: `_run_job` starts `Popen` before attaching it to the job under the lock; cancellation in that interval sees `_process is None`, marks the job CANCELLED, and returns while the new downloader continues. Use a process-launch/termination strategy that reliably stops and waits for the actual downloader and its children on supported platforms, and make process registration atomic with cancellation (or have the worker detect cancellation after launch and terminate before returning). Do not report cancellation success until process-tree termination is confirmed. If cancellation cannot be confirmed, keep/report a recoverable failure state and return an error. Add a wrapper/child process test that confirms both PIDs stop, a deterministic launch-registration race test, and termination-failure coverage; do not invoke external services.

2. **Make staging publication and completion one transaction.** The new worker calls `os.replace(staging_file, target_file)` before `create_manifest`. If manifest creation fails, the job becomes FAILED after the prior target has already been overwritten. Cancellation can also win after `os.replace` but before the worker marks COMPLETED, leaving a CANCELLED job whose final target was replaced. Verify/prepare the manifest from staging first, then coordinate final publish and terminal-state transition with cancellation so exactly one terminal outcome wins. On any pre-publish failure/cancellation, preserve an existing target and remove only this job's staging output. Add deterministic tests for manifest-creation failure preserving the prior target and cancellation racing the publish/completion boundary, in addition to the existing publication and cleanup cases.

3. **Close polling response races and prove terminal protection.** App-level generation protects against a different job replacing the current one, but repeated `setInterval` polls can overlap. Sequence-guard individual responses and preserve monotonic bytes/progress. The added `TC-P09-07` only asserts that percentage does not return to 15%; it does not assert byte monotonicity or release a stale RUNNING response after COMPLETED to prove terminal-state protection. Extend it (or add a focused test) to hold a poll, receive a later RUNNING update and then a terminal update, release the held stale response last, and assert both bytes/progress and terminal state remain unchanged. Use request-start/release signals, not fixed waits.

4. **Keep UI success aligned with backend confirmation.** Make the cancel flow consume and validate the server response and reconcile with status. Never synthesize a CANCELLED job in the client when the status request fails unless the cancel endpoint response itself explicitly confirms terminal cancellation. Display a useful error and continue status recovery otherwise. Add a test for a successful-looking but non-terminal/malformed cancel response plus status-fetch failure.

5. **Correct per-spec verification counts in the report.** The reported combined total of 85 is correct, but the independent combined run produced these counts: globe-box 2; Core Phase 01 16; Core Phase 01 contract review 1; Core Phase 02 10; Core Phase 02 identity review 6; Core Phase 03 7; Core Phase 04 5; Selected Phases 05, 06, 07, 08, and 09 respectively 7, 7, 10, 8, and 6. Update the report breakdown to match; do not change the total unless rerun results differ.
