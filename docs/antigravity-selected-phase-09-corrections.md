## Required corrections

1. **Cancellation must stop the downloader process tree and close process-registration races.** The worker's post-launch cancellation branch catches `_terminate_process_tree` failures, discards the error, and still marks the job `CANCELLED`. The Windows helper can also kill the shell and verify only `proc.poll()`, without confirming its child is gone. There is a launch race: `_run_job` starts `Popen` before attaching it to the job under the lock; cancellation in that interval waits for registration, but the new test simulates registration with a separate hand-written thread rather than exercising `_run_job`. Make the actual worker launch/registration path coordinate cancellation. Do not report cancellation success until the process tree is confirmed stopped. Surface failure without a false `CANCELLED` state. Add a deterministic test that patches/holds the actual `Popen` call in `_run_job`, and verify termination failure is not swallowed by the worker. Preserve the passing wrapper/child process test.

2. **Make staging publication and manifest persistence rollback-safe.** The worker now prepares manifest data before touching the target, but inside the commit block it calls `os.replace(staging_file, target_file)` before writing `manifest_out_path`. If manifest-file creation/write fails, the job becomes FAILED after replacing a prior valid target. Preserve/restore an existing target and avoid leaving a published file without its manifest if any commit step fails. Coordinate target publication, manifest persistence, and `COMPLETED` with cancellation so exactly one terminal result wins. The current `test_15_manifest_creation_failure_preserves_prior_target` only manually sets FAILED and deletes the staging file; it never runs the worker or injects a manifest failure. `test_16_cancellation_racing_publish_boundary` calls cancellation before a manually simulated boundary, but does not run a concurrent worker. Replace these with deterministic tests that exercise the actual worker/commit path, including manifest write failure and cancellation on both sides of the publish point.

3. **Keep UI completion data aligned with the backend response schema.** FastAPI returns `DownloadJobInfo.manifest` as a `ManifestRecord`; the UI completion card reads `activeJob.manifest_file`, a field the backend response does not provide. Current Playwright fixtures supply the nonexistent `manifest_file`, hiding the integration mismatch. Read the returned `manifest` object (or add a deliberate API alias) and use backend-schema-faithful fixtures. Verify a response shaped like the real `DownloadJobInfo` displays the actual manifest filename and refreshes the manifest list.
