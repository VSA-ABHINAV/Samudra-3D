## Required corrections

1. **Cancellation must stop the downloader process tree.** `backend/app/data/download_manager.py` launches a command with `subprocess.Popen(..., shell=True)`, but `cancel_job` only calls `terminate()` and possibly `kill()` on the shell process, suppresses failures, and still returns success. On Windows this can leave the Copernicus child process running while the API/UI says CANCELLED. Use a process-launch/termination strategy that can reliably stop and wait for the actual downloader and its children on supported platforms. Do not report cancellation success until termination is confirmed. If cancellation cannot be confirmed, keep/report a recoverable failure state and return an error instead of pretending the job stopped. Add tests that prove the worker's actual child is stopped and termination failure is surfaced; do not invoke external services.

2. **Write to staging output and publish atomically.** The generated CLI command currently writes directly to `target_file` (`--output-filename` is the final `.nc` name), while the worker/cancel code only deletes a separate `part_file` that the command never writes. A failed or cancelled transfer can therefore leave a partial final `.nc` file, and a pre-existing valid target can be overwritten. Make each job write to a unique same-filesystem staging path, derive live progress from that job's staging file only, and atomically publish it to the final target only after successful process completion and verification. On cancellation/failure remove only that job's staging output and preserve any previous valid final file. Create the manifest from the published target. Add focused tests for cancellation/failure cleanup, successful atomic publication, preserving a previous target, and progress never counting bytes from a prior target.

3. **Close polling response races.** App-level generation protects against a different job replacing the current one, but repeated `setInterval` polls can overlap and an older RUNNING payload can arrive after a newer payload and reduce progress. Serialize polls or sequence-guard individual poll responses. Add a deterministic held-poll test showing a stale response cannot regress bytes/progress or replace a terminal state.

4. **Keep UI success aligned with backend confirmation.** Make the cancel flow consume and validate the server response and reconcile with status. Never synthesize a CANCELLED job in the client when the status request fails unless the cancel endpoint response itself explicitly confirms terminal cancellation. Display a useful error and continue status recovery otherwise. Add a test for a successful-looking but non-terminal/malformed cancel response plus status-fetch failure.

5. **Correct per-spec verification counts in the report.** The reported combined total of 85 is correct, but the independent combined run produced these counts: globe-box 2; Core Phase 01 16; Core Phase 01 contract review 1; Core Phase 02 10; Core Phase 02 identity review 6; Core Phase 03 7; Core Phase 04 5; Selected Phases 05, 06, 07, 08, and 09 respectively 7, 7, 10, 8, and 6. Update the report breakdown to match; do not change the total unless rerun results differ.
